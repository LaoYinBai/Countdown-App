# 🗓️ Countdown App

> 一个因为“不想给倒数日 App 看广告”，于是自己做出来的 Android 小工具。

这是我比较早期的一个 Android 项目。

起因非常简单：当时想找一个轻量的倒数日应用，但市面上不少同类产品要么广告很多，要么塞入了大量我并不需要的功能。

既然需求并不复杂，那就自己做一个。

于是有了这个项目。

---

## ✨ 它是什么

Countdown App 是一个本地运行的 Android 倒数日 / 纪念日应用，主要用于记录生日、纪念日、考试、计划节点以及其他值得记住的日期。

功能并不追求“大而全”，核心目标只有一个：

**把我真正会用到的东西做好。**

目前包含：

* 📅 阳历 / 农历日期
* ⏳ 普通倒数日
* 🔁 每年重复纪念日
* 📌 事件置顶
* 👈 左滑删除 / 👉 右滑置顶
* ☑️ 多选与批量删除
* 🖼️ 自定义卡片背景
* 🔍 事件详情
* 📤 卡片图片导出
* 🎨 根据背景自动调整文字显示
* ✨ 基础动画与交互反馈

---

## 📱 简单使用教程

这个应用本身没有复杂的学习成本。

### 1. 添加一个倒数日

打开应用后，点击首页的添加按钮。

填写事件名称，然后选择目标日期。

你可以选择：

* 阳历日期
* 农历日期
* 是否每年重复

确认后，事件会出现在首页。

---

### 2. 查看事件详情

直接点击事件卡片，即可进入详情界面。

详情页会展示：

* 事件名称
* 剩余天数
* 目标日期
* 自定义背景

也可以在这里修改事件信息。

---

### 3. 删除或置顶

在首页事件卡片上：

```text
← 左滑：删除
→ 右滑：置顶 / 取消置顶
```

置顶后的重要事件会优先显示，并使用更醒目的大卡片样式。

置顶为**互斥**语义：置顶一个事件会自动取消其他事件的置顶，因此全局至多保留 1 个置顶。

---

### 4. 批量管理

进入编辑模式后，可以：

* 选择多个事件
* 全选
* 取消选择
* 批量删除

适合一次整理较多倒数日。

---

### 5. 设置背景

进入事件详情页后，可以从手机相册中选择图片作为卡片背景。

应用会根据背景亮度自动调整文字颜色，尽量保证内容可读。

---

### 6. 保存卡片

在详情页可以将当前倒数日卡片导出为 PNG 图片并保存到手机相册。

适合分享生日、纪念日或者重要节点。

## 🧭 为什么这个仓库还留着

现在回头看，这个项目的工程规模并不大。

它本质上是一个非常典型的单端 Android 应用：

```text
UI
 ↓
ViewModel
 ↓
Repository
 ↓
Room
```

状态、数据、交互和持久化基本都发生在同一台设备、同一个应用内部。

这意味着它的系统边界非常清楚。

但也正因为如此，我选择把这个仓库一直公开保留下来。

它记录了一个很具体的阶段：

**我第一次尝试让 AI 不只是回答编程问题，而是真正参与完成一个可以安装、可以使用、具有完整交互流程的软件。**

它不是一个为了展示架构能力而设计的项目。

它首先是一个工具。

然后才是一个工程实践。

---

## 🤖 关于 Vibe Coding

这个项目的大量开发工作都在 AI 辅助下完成。

如果按照后来流行起来的说法，它完全可以被归入 **Vibe Coding**。

我并不打算避讳这一点。

恰恰相反，我觉得这个仓库留下来很有意义。

AI 确实已经可以大幅降低一个人把想法变成软件的成本。

你可以描述一个需求，让模型生成 UI、数据库、业务逻辑，再通过不断反馈把它逐渐修成一个真正可以运行的产品。

Countdown App 就是这种开发方式很直接的产物。

但后来做了更多工程以后，我对 Vibe Coding 的理解也发生了一些变化。

### 生成代码，并不等于完成软件工程

对于 Countdown App 这样的单端应用，大多数问题可以被限制在一个相对清晰的边界里：

```text
用户操作
→ UI 状态变化
→ ViewModel
→ 数据操作
→ Room
→ UI 更新
```

因此 AI 很容易参与其中。

但当系统逐渐涉及多个进程、多个设备、多个操作系统、网络通信、状态同步、失败恢复、版本兼容和长期维护以后，真正困难的事情会逐渐从：

> “代码怎么写？”

变成：

> “系统应该怎么组织？”

再继续变成：

> “哪里应该复杂，哪里必须保持简单？”

AI 可以很好地执行任务。

但需求边界、系统架构、复杂度控制、失败模型以及最终验收，依然需要有人负责。

所以今天如果让我重新描述 Vibe Coding，我更愿意把它看成：

**一种新的软件生产方式，而不是软件工程本身的替代品。**

Countdown App 正好记录了我开始理解这件事之前的那个阶段。

## 🛠️ 技术栈

项目使用：

| 部分             | 技术                    |
| -------------- | --------------------- |
| Language       | Kotlin                |
| UI             | Jetpack Compose       |
| Design         | Material 3            |
| Local Database | Room                  |
| State          | ViewModel + StateFlow |
| Architecture   | Repository            |
| Image          | Coil                  |
| Lunar Calendar | `cn.6tail:lunar`      |
| Animation      | Compose Animation     |

项目整体保持单 Activity + Compose 的结构。

## 🚀 构建

### 环境

* Android Studio
* JDK 17
* Android SDK 34
* Min SDK 26

### 克隆项目

```bash
git clone https://github.com/DSGYDS/Countdown-App.git
cd Countdown-App
```

使用 Android Studio 打开项目即可。

### 命令行构建

Linux / macOS：

```bash
./gradlew assembleDebug
```

Windows：

```powershell
.\gradlew.bat assembleDebug
```

生成的 Debug APK 位于：

```text
app/build/outputs/apk/debug/
```

## 🧩 项目定位

这个仓库现在更适合被理解为：

**一个完整的小型 Android 应用，以及一份早期 AI 辅助软件开发实践记录。**

它并不代表我现在处理复杂软件系统时采用的完整工程标准。

例如，对于一个长期维护、具有大量真实用户、需要处理版本迁移和复杂失败场景的软件，我会对：

* 数据迁移
* 错误恢复
* 模块边界
* 可测试性
* 日志
* 状态一致性
* 发布流程
* 兼容策略

提出明显更严格的要求。

但我同样不会因为后来掌握了更多工程方法，就回头把这样一个小工具重构成“航空母舰”。

它解决的问题很简单。

那么它就应该保持简单。

这是我现在反而更加看重的一条原则：

> **工程能力不是把所有项目都做复杂，而是知道一个问题究竟值得多少复杂度。**
